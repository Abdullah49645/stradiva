# Evaluation: method, results, reproduction

The numbers live in **docs/EVALUATION_RESULTS.md**, which is generated by
`evaluation/build_report.py` from `evaluation/results/`. The same file feeds
the UI's "How it was tested" and "Real dashcam footage" tabs. This document
explains how each number was produced, what it can and cannot show, and how
to reproduce it. No number below was typed in by hand.

## 1. Principles

* **Ground truth never enters the pipeline.** `backend/pipeline/analyze.py`
  takes a video file and a stated prior, and nothing else. Simulator ground
  truth is read only by the scoring code.
* **Splits fixed in advance, development on dev only.**
  `collision_suite.sample_scenario` uses seed bases dev 1000, test 5000 and
  shift 9000. All tuning happened on dev. Test and shift were run once, on
  frozen code (section 6).
* **Layered evaluation**, so each layer's errors are visible on their own:
  1. geometry against the simulator's exact homography;
  2. the reasoning layer on tracks built from ground-truth ground contacts
     plus 0.7 px noise. `oracle_clean` has no occlusion. In `oracle_occluded`,
     the farther vehicle is unmeasured whenever the nearer one's true box
     overlaps it;
  3. the full pipeline from pixels (`e2e`).
* **Scoring punishes confident errors, not refusals.** The outcomes are:
  * **correct**, including "no collision" when none happened;
  * **correct refusal**: the event was off-screen;
  * **no verdict / qualified**: CARAI declined, or answered "depends on the
    assumptions", where the truth was definite;
  * **missed collision**: a visible collision reported as "no contact found";
  * **false collision**;
  * **wrong contact time**: a verdict whose contact is more than 0.3 s from
    the true one;
  * **overconfident**: a definite verdict where the truth depends on the
    assumptions;
  * **opposite verdict**.

  The last five are "harmful". The ground-truth verdict is computed
  independently (`collision_suite.gt_counterfactual`): the follower's true
  motion is replayed with braking at a after reaction time r, on the same
  grid and envelope CARAI uses.
* **Failures are reported.** Real-footage tests were pre-registered
  (`evaluation/real/PREREGISTRATION*.md`), with a Deviations section for
  anything changed afterwards. The holdout failed, and that failure leads
  the real-footage section.

## 2. Collision suite (simulation)

**Scenes** (`evaluation/experiments/collision_suite.py`): 6 s at 30 fps,
1280×720. There are four camera families: overhead or roadside pole, with
traffic receding from or approaching the camera. Each scene has a lead that
brakes at 4.5–8 m/s², and a follower that brakes (85 % of scenes) after a
true reaction time of 0.5–2.6 s, or not at all.

What is randomised:
* **Markings:** the true cycle is drawn from N(12 m, 3 %) on dev and test
  and N(12 m, 5 %) on shift. CARAI always assumes 12 m ± 3 %, so on shift
  its stated prior is too narrow on purpose. Edge offset, wear and paint
  contrast vary too.
* **Camera:** roll, yaw, height, pitch and focal length.
* **Image:** noise, blur, fog and brightness.

**Shift** over-samples approaching traffic and widens every range.

**What it cannot show.** The simulator draws vehicles as shaded 3D boxes.
Real vehicles, lighting, shadows, compression and clutter are harder, so
treat end-to-end numbers as an upper bound for real footage. The reasoning-
layer numbers are less sensitive to this, because their input is
ground-contact tracks.

**Results:** EVALUATION_RESULTS.md, sections "Held-out test split" and
"Distribution-shift split". Failure breakdowns are under "Where the full
pipeline fails" (by distance and by camera family). The v1 pipeline on the
same clips is under "Before and after".

**Development history.** Every scored dev run is kept in
`evaluation/results/dev_history/` and re-scored with the final rules. The
main changes it records:
* Iteration 1 → 2 removed the reasoning layer's false collisions. Before,
  contact was extrapolated to within 0.04 s of the clip end, or rested on
  the vehicle-length prior alone. The rule now requires a contact, and a
  "no contact", to survive ±2σ of vehicle length. The occluded oracle was
  also fixed to hide the farther vehicle, not always the lead.
* Scoring became stricter between iterations: missed collisions and
  wrong-time contacts were split out as harmful outcomes.
* **Background ablation** (dev, end to end; `ablation_bg_*.jsonl`): the
  whole-clip median with a first-half fallback (v2 at the start of this
  work), against region-resolved segment medians with 3 or 5 segments. The
  chosen variant and its numbers are in EVALUATION_RESULTS.md.
* **Tracking diagnostics** (`track_diagnostics.py`, `track_diag_*.json`)
  report, per scene, how much of each true vehicle's visible time a track
  covers, its identity breaks, and its contact-point error in pixels.

## 3. Geometry before and after (same scenes)

`legacy_geometry_sweep.py` (v1, as received) and `geometry_sweep_v2.py`
run on the same 18 cached renders. They vary roll (including non-integer
angles), yaw, camera pose, and true markings that differ from the assumed
standard. Both report the error in along-road displacement of the true
ground-contact track mapped through the recovered homography, which is the
speed error for a constant-speed vehicle. In the "prior mismatch" scenes, v2
is scored against the error the wrong prior implies. A dash-cycle length
cannot be identified from one static view, so reproducing the prior's error
exactly is correct behaviour. Whether the duty-cycle check notices a
proportion change is reported separately.

## 4. The Skeptic under fault injection

`skeptic_faults.py` uses 8 scenes × 7 conditions, analysed by the unchanged
pipeline:
* clean (this gives the false-alarm rate);
* camera knocked 1.5° mid-clip;
* wrong marking shape (6 + 12 m, against an assumed 3 + 9 m);
* dash indices shifted by one cycle, injected in code;
* wrong lane-width prior;
* two negative controls that no check can see from one static camera:
  longer markings with the same proportions, and a wrong frame rate in the
  file metadata.

Reported per condition:
* how often the verdict was withheld or the footage refused;
* how often any check flagged;
* silent failures: speed error above 10 % with no flag;
* the median worst speed error.

## 5. Real footage: dashcam ego speed

| Dataset | Rights | Role |
|---|---|---|
| comma.ai speedchallenge `train.mp4` (17 min, 20 fps, freeway then city, per-frame speed labels) | No licence file. Evaluation only, not redistributed, fetched by `evaluation/real/fetch_comma.sh` with a SHA-256 check | First pre-registered test (commit 22aacf7), estimator frozen at 2bf75b9 |
| comma2k19 Example_1 segment 40 (1 min, city street, CAN speed, sensor timestamps) | MIT | Independent holdout, pre-registered in commit 074a1fd |

**Pre-registered speedchallenge result.** On the freeway, CARAI answered a
minority of 2 s windows, with a median error of a few percent and 90 %
interval coverage near nominal. In the city, the freeway marking prior is
wrong and CARAI answered almost nothing, but what it did answer was wrong.
The failure analysis is in the Deviations section of
PREREGISTRATION.md. Two checks were added after it (duty cycle and
continuity), with tolerances set on synthetic data only. Re-running on this
video is labelled post hoc.

**Pre-registered holdout: failed.** It was run with the fixed estimator
and the Caltrans freeway prior. The segment turned out to be a city street
with shorter markings, so CARAI gave 16 confident answers, all about 2×
too fast. We report this as the primary real-footage result.

**Post hoc.** A second ruler was added: lane width (3.6 m ± 10 %) together
with the camera's focal length gives the scale independently of the
markings. It rejects the freeway prior on this segment, and CARAI answers
nothing instead of answering wrongly. Re-running with the 24 ft city
standard the check points to gives a median error of a few percent. Because
that standard was chosen after seeing the data, this is a demonstration,
not a validation.

Units: the speedchallenge labels are undocumented. They are taken as m/s
from scene context (freeway values of 23–28), and this inference was
recorded in the pre-registration before any comparison.

## 6. Freeze, and what was run after it

The code freeze is the git tag `eval-freeze`. After the tag, the test and
shift splits (all three layers), the Skeptic fault injection, and the v2
geometry sweep were each run once. Any later code change is listed in
docs/EVALUATION_RESULTS.md under "Changes after the freeze". If that
section is absent, there were none.

## 7. Reproduce

```bash
pip install -r requirements-dev.txt
python3 -m pytest -q tests                                   # unit, integration, AWS handlers (moto)

cd evaluation/experiments
python3 collision_suite.py --split test  --n 30 --mode oracle_clean
python3 collision_suite.py --split test  --n 30 --mode oracle_occluded
python3 collision_suite.py --split test  --n 30 --mode e2e         # also runs the v1 pipeline (ablation)
python3 collision_suite.py --split shift --n 30 --mode e2e         # etc.
python3 summarize_suite.py
python3 skeptic_faults.py --n 8
python3 legacy_geometry_sweep.py && python3 geometry_sweep_v2.py

bash ../real/fetch_comma.sh                                  # speedchallenge (evaluation only)
python3 ../real/run_comma_eval.py --prior california_freeway
python3 ../real/run_comma2k19_holdout.py                     # needs the comma2k19 Example_1 segment

cd ../.. && python3 evaluation/build_report.py               # regenerates EVALUATION_RESULTS.md and the UI data
```

Each simulator scene is rendered deterministically from its seed into
`evaluation/_sim_cache/` (gitignored). A full test or shift e2e run takes
about 10–15 minutes on 2 CPU cores.
